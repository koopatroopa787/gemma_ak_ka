# LIMITATIONS.md

This document describes what Pharos cannot do, why we made the technical decisions we did, and what the production version would require. We include it because intellectual honesty about capability boundaries is more useful to the field than overclaiming.

---

## Model Capability Ceiling

**Gemma 4 E2B is not a forensic instrument.** We do not ask it to be one.

The E2B vision encoder processes images at a general-purpose level. It reliably performs:
- OCR of clearly printed text (batch codes, expiry dates, medicine names)
- Structural understanding of packaging layout
- Identification of obviously missing or inconsistent elements
- Structured JSON output following a schema

It does **not** reliably perform:
- Sub-millimetre print registration analysis
- Hologram authenticity verification (requires controlled illumination angles and spectrometric analysis)
- Micro-texture classification of packaging materials
- Detection of subtle ink chemistry differences

**Why this matters:** Real-world counterfeit detection at forensic certainty requires spectrometers, polarised light microscopy, and mass spectrometry. Pharos provides a first-pass triage tool, not a definitive authentication system.

## The Offline Constraint

Pharos processes images entirely on-device. This is a deliberate design choice, not a technical limitation:

1. Many target settings (rural pharmacies, mobile clinics) have unreliable connectivity
2. Medicine supply chain data is sensitive — pharmacist scan records should not transit external networks
3. On-device processing eliminates a class of privacy risks

**What this means for the registry:** The WHO Medical Product Alert data embedded in the registry reflects the state of alerts at the time of app installation. The app must sync when online to receive new alerts. A pharmacy offline for 30+ days may miss recent alerts.

## False Positive Risk

Flagging authentic medicine as suspicious has real costs: a pharmacist may withhold medicine from a patient who needs it.

We calibrate the model toward lower false positive rates at the expense of some sensitivity. A `MODERATE` risk rating means "verify before dispensing," not "do not dispense." The pharmacist makes the final decision.

## What the Production Version Requires

This hackathon prototype demonstrates the architectural approach. A production deployment would require:

1. **Clinical validation study** — prospective evaluation against a ground-truth authenticated sample set in target settings
2. **Regulatory review** — as a decision-support tool used in pharmaceutical contexts, regulatory classification varies by jurisdiction
3. **Larger fine-tuning dataset** — minimum 5,000 labeled images across 200+ medicines from 50+ manufacturers
4. **Formal differential privacy** — local differential privacy with calibrated epsilon for the resistance surveillance layer (Layer 2, deferred)
5. **Offline sync protocol** — CRDT-based sync architecture for the multi-pharmacist counterfeit reporting network (deferred)
6. **Security audit** — the evidence signing system uses Ed25519; a production deployment requires third-party cryptographic audit

## Existing Systems We Acknowledge

mPedigree, Sproxil, and PharmaSecure provide SMS-based medicine authentication in several African markets. These systems verify authenticity via unique codes printed on packaging.

Pharos is complementary, not competitive. SMS verification requires: (a) the pack to have been enrolled in the SMS system, (b) connectivity at verification time, and (c) the counterfeit not to have copied the code from an authentic pack (code copying is a documented attack vector).

Pharos provides a visual inspection layer that works offline, on un-enrolled packs, and is harder to defeat by code copying.
